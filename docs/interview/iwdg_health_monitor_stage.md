# IWDG 看门狗与任务健康监测阶段

## 阶段目标

本阶段给项目增加可靠性保护：

- 每个关键任务周期性上报 alive；
- `HealthMonitorTask` 统一检查任务是否超时；
- 只有所有关键任务都健康时才喂 IWDG；
- 如果关键任务卡死，系统停止喂狗，最终由 IWDG 复位。

## 为什么要写看门狗

### 问题

为什么一个已经能正常采集传感器、显示屏幕、串口通信的项目，还需要加入看门狗？

### 操作

看门狗可以理解成一个“系统自救定时器”。

嵌入式系统经常需要长时间运行，运行过程中可能遇到：

- 某个任务进入死循环；
- I2C 读传感器时卡死；
- 内存异常；
- 中断异常；
- 程序跑飞；
- 外设状态异常。

如果没有看门狗，系统可能会一直卡在异常状态。

加入 IWDG 后，如果系统长时间没有正常喂狗，硬件会自动复位 MCU，让系统重新从启动流程恢复。

### 观察

看门狗本质上是一个倒计时定时器。比如当前项目近似设置为 6 秒超时：

```text
正常运行：
6 -> 5 -> 4 -> 喂狗 -> 重新变成 6

异常卡死：
6 -> 5 -> 4 -> 3 -> 2 -> 1 -> 0 -> MCU 自动复位
```

所以：

```text
喂狗 = 告诉硬件：系统当前还健康
不喂狗 = 允许硬件在超时后复位系统
```

### 结论

看门狗的意义不是让系统“永远不出错”，而是让系统在出错后具备自动恢复能力。

它把项目从：

```text
传感器能采集
屏幕能显示
串口能通信
```

提升到：

```text
系统异常时能够自动恢复
```

这是嵌入式项目工程化和可靠性设计中非常重要的一步。

## 为什么不能每个任务自己喂狗

### 问题

如果让每个任务都自己喂狗，会有什么问题？

### 操作

本项目采用集中式喂狗策略：

```text
业务任务 -> AppHealth_Report()
HealthMonitorTask -> 检查所有任务
HealthMonitorTask -> 全部健康才喂 IWDG
```

### 观察

如果某个任务卡死，它不再调用 `AppHealth_Report()`。

`HealthMonitorTask` 会打印：

```text
HEALTH FAIL task=xxx now=... last=... timeout=...
HEALTH IWDG feed skipped, waiting for reset if fault persists
```

如果故障持续存在，IWDG 超时后 MCU 会复位。

### 结论

集中式喂狗比“每个任务自己喂狗”更可靠。

如果每个任务都能喂狗，那么即使 DHT11 任务卡死，MPU 任务仍然可能继续喂狗，系统不会复位，故障被掩盖。

集中式策略要求所有关键任务都健康，才允许喂狗。

## 当前监控的任务

当前被监控的任务：

```text
HEART
WORKER
SYSMON
CONTROL
DHT11
MPU
VL53
POT
LCD
SLOG
```

没有监控：

```text
CMD
COMMTX
```

原因：

- `CMD` 可能长时间没有串口命令，正常阻塞在队列上；
- `COMMTX` 在二进制协议帧关闭时可能长时间没有发送数据；
- 它们不周期运行，不能用“多久没上报 alive”判断是否卡死。

## IWDG 参数

当前配置：

```text
IWDG clock: LSI，约 32kHz
prescaler: 64
reload: 3000
approx timeout: 约 6 秒
Health check period: 1 秒
startup grace: 3 秒
```

由于 LSI 不是精密时钟，IWDG 超时时间是近似值。

## 面试回答

问题：你的项目里看门狗是怎么设计的？

30 秒回答：

我没有让每个任务直接喂狗，而是做了一个 `HealthMonitorTask`。关键任务每个周期调用 `AppHealth_Report()` 上报心跳，HealthMonitor 每 1 秒检查所有关键任务的最近上报时间。只有全部任务都没有超时，HealthMonitor 才会刷新 IWDG。如果某个任务卡死，它的心跳不再更新，HealthMonitor 会停止喂狗，最终 IWDG 超时复位系统。这样可以避免某个正常任务继续喂狗而掩盖其他任务卡死的问题。

## 常见追问

### 问题：为什么不监控 CMD 和 COMMTX？

因为它们不是固定周期任务。

`CMD` 没有串口命令时应该阻塞等待，`COMMTX` 在二进制帧关闭时也可能没有数据可发。不能因为它们长时间不运行就认为系统异常。

### 问题：IWDG 和 WWDG 有什么区别？

IWDG 使用独立低速时钟 LSI，独立于主系统时钟，适合系统跑飞时复位。

WWDG 使用 APB 时钟，并带窗口限制，更适合检测喂狗过早或过晚的问题，但使用复杂度更高。

当前项目选择 IWDG，是因为目标是先实现系统级故障恢复。
