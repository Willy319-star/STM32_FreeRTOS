# FreeRTOS 任务优先级设计记录

> 约定：以后如果修改任务优先级，需要同步更新本文档。

## 当前优先级总览

当前项目使用 `tskIDLE_PRIORITY` 作为基准。

```text
优先级 0
    Idle Task

优先级 tskIDLE_PRIORITY + 2
    DHT11
    MPU
    VL53
    POT
    CMD

优先级 tskIDLE_PRIORITY + 1
    HEART
    WORKER
    SYSMON
    COMMTX
    CONTROL
    LCD
    SLOG
    HEALTH
```

## 为什么这样设置

### 问题

多传感器 FreeRTOS 项目中，任务优先级应该如何分配？

### 操作

按照任务实时性和职责分层：

1. 数据输入源优先级稍高；
2. 显示、日志、通信、监控优先级稍低；
3. 所有任务都必须通过 delay、queue、semaphore 等机制主动阻塞；
4. 空闲时进入 IdleHook/WFI。

### 观察

传感器任务：

```text
DHT11  2s 周期
MPU    100ms 周期
VL53   500ms 周期
POT    500ms 周期
```

这些任务采集完数据后都会 `vTaskDelayUntil()`，不会一直占用 CPU。

命令任务 `CMD` 阻塞等待 UART RX 队列，只有收到命令才运行。

显示、日志、通信、告警和系统监控任务都属于数据消费或状态观察任务，可以稍微滞后。

### 结论

当前优先级策略是：

```text
采集/输入优先
显示/日志/监控稍后
空闲时进入低功耗等待
```

这样既保证采样及时性，又避免日志和显示影响传感器采集。

## 为什么 SLOG 没有设成 +2

`SLOG` 是传感器队列的消费者，负责：

- 更新显示快照；
- 提交通信消息；
- 更新告警 EventGroup；
- 打印文本日志。

目前采样频率不高，`SLOG` 使用 `+1` 足够消费队列。

如果以后提高 MPU6050 采样频率，例如 10ms 一次，可以考虑：

- 把 `SLOG` 提升到 `+2`；
- 降低文本日志频率；
- 把数据处理和文本日志拆成两个任务；
- 增大 sensor queue 长度。

## 为什么 HEALTH 是 +1

`HEALTH` 是健康监测和 IWDG 喂狗任务。

它不需要抢占传感器采样，不需要毫秒级实时，只需要每 1 秒检查一次任务健康状态。

所以它设置为：

```text
tskIDLE_PRIORITY + 1
```

这能保证：

- 不抢占传感器采集任务；
- 又不会低到长期得不到调度；
- 适合做系统级监控。

## 面试回答

问题：你项目里的任务优先级是怎么设计的？

30 秒回答：

我把任务优先级按实时性分层。传感器采集任务和串口命令任务设为 `tskIDLE_PRIORITY + 2`，因为它们是数据输入源，需要及时响应采样周期或 PC 命令。显示、日志、通信发送、系统监控、告警监控和健康监测设为 `+1`，因为它们更多是消费数据、展示状态或周期性检查，可以稍微滞后。所有周期任务都会用 `vTaskDelayUntil()` 或队列阻塞主动让出 CPU，所以不会因为优先级高而长期占用处理器。系统空闲时会进入 IdleHook，并执行 `WFI`。
