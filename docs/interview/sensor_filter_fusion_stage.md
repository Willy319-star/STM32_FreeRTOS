# 传感器滤波与状态融合阶段

## 这一阶段做了什么

本阶段在传感器生产者任务中加入轻量滤波和状态判断：

```text
DHT11    保留上一次有效温湿度
VL53L0X  距离滑动平均
MPU6050  简单运动阈值和姿态变化判断
ADC      电位器平均滤波和死区去抖
```

滤波后的数据继续通过原来的 `s_sensor_queue` 发送给汇总任务。

## 问题

为什么传感器数据不能直接使用原始值？

## 操作

不同传感器的噪声特点不同：

```text
DHT11    偶发读取失败，但温湿度变化慢
VL53L0X  距离可能轻微跳动
MPU6050  高频数据容易受瞬时扰动影响
ADC      电位器边界附近会抖动，导致页面来回切换
```

所以不能用一个统一滤波方法处理所有传感器，而是按传感器特性分别处理。

## 观察

串口日志中会看到：

```text
DHT11 STALE ...
VL53L0X RANGE_OK ... filtered=1
MPU6050 OK ... motion=0 posture=0
POT OK ... filtered=1 status=avg
```

这些字段表示当前数据已经经过处理或状态判断。

## 结论

滤波的目的不是让数据“看起来好看”，而是让显示、告警、协议上报更稳定。

## DHT11：保留上一次有效值

### 问题

DHT11 偶发失败时，是否应该马上把温湿度显示成无效？

### 操作

DHT11 读取成功时：

```text
更新 last_temp
更新 last_hum
stale=0
```

DHT11 读取失败但之前有成功值时：

```text
使用 last_temp / last_hum
stale=1
保留错误原因
```

### 观察

如果某次读取失败，但之前有有效值，会打印：

```text
DHT11 STALE tick=... temp=23C hum=54% last=no-response-low reads=... err=...
```

### 结论

温湿度变化很慢，偶发一次失败时保留上一次有效值比直接显示失败更合理。

但日志仍然保留 `STALE` 和错误计数，避免把问题隐藏掉。

## VL53L0X：滑动平均

### 问题

为什么 VL53L0X 距离要滑动平均？

### 操作

本项目保留最近 5 次有效距离：

```text
distance_window[5]
```

每次测到有效距离后，放入环形窗口，然后计算平均值。

### 观察

如果原始距离在小范围内跳动，输出距离会更平滑。

串口会显示：

```text
VL53L0X RANGE_OK ... dist=... filtered=1
```

### 结论

滑动平均适合处理短时间随机抖动。

代价是响应速度稍慢，因为输出值会受到前几次采样影响。

## VL53L0X 离线诊断与 I2C 恢复

### 问题

如果日志出现：

```text
VL53L0X FAIL ... model=0x00 status=offline
```

这说明问题不在滑动平均，而是在更前面的 I2C 识别或初始化阶段。

### 操作

本阶段增加了 I2C2 总线恢复：

```text
SDA 释放为高
手动给 SCL 输出 9 个时钟
发送 STOP
重新尝试 VL53L0X_Init()
```

同时增加诊断日志：

```text
VL53L0X diag i2c_ready=... model=0x.. status=... offline_count=...
```

### 观察

如果看到：

```text
i2c_ready=0 model=0x00
```

优先检查接线、供电、GND、SCL/SDA 是否接反。

如果看到：

```text
i2c_ready=1 model=0xEE
```

说明 I2C 能找到设备，问题更可能在初始化或测距流程。

如果看到：

```text
status=addr-nack
```

说明 0x29 地址没有 ACK，优先看 I2C 总线或模块供电。

如果看到：

```text
status=model-read-fail
```

说明 0x29 可能 ACK 了，但读 `MODEL_ID` 寄存器失败，优先怀疑 I2C 读时序或设备内部页状态。

如果看到：

```text
status=model-id-mismatch
```

说明读到了寄存器，但不是 VL53L0X 期望的 `0xEE`，可能是设备还没完全上电、内部页不对，或总线上有异常响应。

为了避免频繁初始化扰动设备，离线后改为每 2 秒重试一次初始化。

### 结论

滤波只处理有效测距值。

当 `MODEL_ID` 都读不到时，应先解决 I2C 在线问题，而不是调整滑动平均窗口。

## MPU6050：运动和姿态变化判断

### 问题

MPU6050 输出很多轴数据，项目里如何提炼成有意义的状态？

### 操作

本阶段做两个简单判断：

```text
motion:
    任意 gyro 轴角速度绝对值 > 20dps

posture_changed:
    任意 accel 轴相比上一次变化 > 120mg
```

### 观察

串口会显示：

```text
MPU6050 OK ... motion=0 posture=0
```

移动或转动板子时，`motion` 或 `posture` 可能变为 1。

### 结论

这里不是复杂姿态解算，只是轻量状态融合：

```text
原始三轴数据 -> 是否运动 / 姿态是否变化
```

这样更适合当前 FreeRTOS 综合项目阶段。

## ADC：平均滤波和死区去抖

### 问题

为什么电位器要滤波？

### 操作

ADC 保留最近 4 次 raw 值做平均。

同时加入 8 raw 的死区：

```text
如果新平均值和上一次滤波值差异 <= 8
    保持上一次滤波值
否则
    更新滤波值
```

### 观察

电位器不动时，raw 和 percent 更稳定。

屏幕页面切换也不容易在边界附近反复跳。

### 结论

ADC 平均滤波减少随机噪声，死区去抖减少边界抖动。

## 为什么在生产者任务里滤波

### 问题

滤波应该放在传感器任务，还是放在汇总任务？

### 操作

当前选择放在传感器生产者任务中。

也就是：

```text
传感器读取原始值
        ↓
当前任务内滤波
        ↓
发送 AppMessage
        ↓
显示/告警/协议使用稳定值
```

### 观察

这样 `TaskSensorLog`、`AppControl_UpdateFromSensor()`、`AppComm_SubmitSensorMessage()` 都不需要重复滤波。

### 结论

对于当前项目，生产者侧滤波更简单，数据流也更清楚。

如果以后需要同时保留“原始值”和“滤波值”，可以扩展 `AppMessage`，同时发送 raw 和 filtered。

## 面试回答

问题：你的项目里传感器数据是怎么处理的？

30秒回答：

我没有直接使用所有原始传感器数据，而是按传感器特点做了轻量滤波。DHT11 因为温湿度变化慢，偶发读取失败时保留上一次有效值，并用 `stale` 标记；VL53L0X 距离使用最近 5 次有效值滑动平均；MPU6050 根据角速度阈值和加速度变化判断运动和姿态变化；电位器 ADC 使用 4 点平均和 raw 死区去抖，避免页面切换抖动。

深入解释：

这些处理放在各自的传感器任务内完成，滤波后的数据再通过 FreeRTOS Queue 发送给汇总任务。这样显示、告警、UART 协议都使用同一份稳定数据，不需要每个消费者重复处理。

追问：

为什么不用卡尔曼滤波？

回答：

当前项目目标是多传感器实时采集节点，传感器频率和精度要求还没有到必须使用卡尔曼滤波的程度。滑动平均、保留上次有效值、阈值判断这些方法实现简单、资源占用低、可解释性强，更适合 STM32F407 + FreeRTOS 的项目阶段。如果后续做姿态解算或高精度融合，再考虑互补滤波或卡尔曼滤波。

## VL53L0X addr-nack 调试补充

### 问题

日志出现：

```text
VL53L0X FAIL ... model=0x00 status=addr-nack
```

这说明 MCU 在 I2C2 上访问 `0x29` 地址时，没有收到 VL53L0X 的 ACK。它发生在读取 `MODEL_ID` 之前，所以不是滤波问题，也不是测距算法问题，而是 I2C 地址探测阶段失败。

### 操作

代码增加了三类诊断和恢复：

```text
1. 软件 I2C 时序从 5us 放慢到 8us
2. 初始化和重试前执行 I2C2 bus recovery
3. 打印 PB10/PB11 当前电平：scl / sda
```

VL53L0X 初始化流程现在变成：

```text
I2C2 初始化
读取 SCL/SDA 是否空闲为高
恢复总线
最多 3 次探测 0x29 是否 ACK
ACK 后再执行 VL53L0X_Init()
失败时打印 i2c_ready/scl/sda/status
```

### 观察

新的诊断日志类似：

```text
VL53L0X diag i2c_ready=0 scl=1 sda=1 model=0x00 status=addr-nack ...
```

判断方法：

```text
scl=1 sda=1 i2c_ready=0
    总线空闲，但 0x29 没有设备应答。重点看模块供电、XSHUT/EN、地址是否真的在 0x29。

scl=1 sda=0
    SDA 被拉低，总线可能被从设备卡住，需要断电重上电或继续做 bus recovery。

scl=0
    SCL 被拉低，可能有外设拉住时钟，或者引脚配置/连线冲突。

i2c_ready=1 model=0xEE
    I2C 地址和模型 ID 都正常，后续问题才进入初始化、校准或测距阶段。
```

### 结论

`addr-nack` 的本质是“地址阶段没有应答”。即使没有动线，也可能由上电时序、模块内部状态卡住、软件 I2C 时序过快、SDA/SCL 被拉低引起。修复思路不是直接改滑动平均，而是先把 I2C 总线状态变成可观察证据，再根据 `scl/sda/i2c_ready/status` 判断下一步。
